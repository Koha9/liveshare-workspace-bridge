## 接続と権限

Live Share Guest ウィンドウの Profile に拡張をインストールします。更新後はそのウィンドウを再読み込みし、対象セッションへ再接続して、agent に `lswb_list_workspaces` を呼び出してもらいます。ルート名と完全な vsls URI でプロジェクトを選びます。再読み込み後のバインドエラーには再検出が必要です。拡張の Output チャネルにパイプの起動エラーが表示されます。ブリッジを診断する人は、インストール済みの拡張ディレクトリから `node extension/cli.cjs instances` または `diagnose` を実行できます。agent は MCP ツールを使います。

再読み込みまたはクラッシュしたウィンドウは検出記録を残すことがあります。そのパイプが存在せず所有プロセスが終了している場合、検出はそのプローブを `ownerProcess: "exited"` 付きの `stale` として報告し、失敗としては数えません。そのような記録しか残っていない場合、状態は `no_records` です。拡張は次回の有効化時にこれらの記録を削除します。

**Live Share Workspace Bridge: Configure Agent Permissions** を開きます。agent アクセスは既定で有効、Host アクセス（`host.enabled`）は既定で無効です。構成値と実効権限を確認します。これらの設定はユーザーが管理し、agent が拒否を迂回するために有効にしてはいけません。権限の変更は新規作業を止めますが、送信済みの効果は戻しません。

## 実行中の切断と復旧

broken pipe の後処理：クライアントのタイムアウト後に遅延応答の書き込みが失敗しても、待受が空回りし続けることはなくなりました。writer の後処理エラーは隔離され、壊れた接続は切断され、待受自体の障害では空回りせず終了します。実際の Windows パイプテストで確認済みですが、ウィンドウのフォーカス喪失が原因であるとは確認されていません。

ready に到達済みの IPC ヘルパーが終了すると、1／2／4 秒後に再起動し、不安定な再起動は最大三回までです。ready の状態が一分続くと回数がリセットされます。フォーカスイベントや Host のポーリングは不要です。起動／ポリシー／アクセスの失敗と明示的な Stop は自動再起動しません。トランスポートの復旧は instance/epoch、Host ジョブ、結果不明状態を保持し、実行中の作業を直列化し、送信済みの操作を再送しません。

それでも切断されたままなら `lswb_status` を確認します（手動で診断している場合は CLI の `diagnose` を一度実行します）。タスクで復旧が許可されている場合、agent は対象の Guest ウィンドウでコマンドパレットから **Live Share Workspace Bridge: Restart Connection**（`liveshareWorkspaceBridge.restart`）を実行できます。Ctrl+Shift+P、または Ctrl+P の後に `>` を入力します。対応する UI ツールがなければ、ユーザーに一度依頼します。手動再起動は instance/epoch を変更し、Host のジョブ／転送ハンドルを無効にするため、ルート名と完全な URI で一度再検出します。Host の結果不明状態は残るため、確認応答の前に Host の復旧を確かめてください。拒否されたアクセス、ポリシーの失敗、意図的な Stop を迂回したり、結果不明の変更を再送したりしてはいけません。IPC の復旧は Live Share への再参加や、見つからない Host 端末の修復は行いません。

## Host 端末がない／応答しない

Host 機能には、読み書き可能な接続済みの共有 Windows PowerShell 端末が一つ必要です。その端末が Host ヘルパーを一度起動し、その後 Host が "Live Share: Share Server" でヘルパーのポートを共有します。通常の Guest 端末は除外します。端末がない場合、agent は Host のセットアップをユーザーに一度依頼して待ちます。候補が複数ある場合は正確な構成名が必要です。繰り返しの依頼、端末の推測、別の実行経路への切り替えはしません。

バインドは所有する一時 bootstrap ファイルを使って共有ルートを検証します。`lswb_host_status` が `handshake.state: "waitingForward"` を示している間は、表示されたポートを共有するよう Host に依頼し、状態をポーリングします。他の Host ツールは `host_handshake_pending` を返します。ハンドシェイクが失敗またはキャンセルされた場合は、再度バインドする前に、前のヘルパーがあれば Ctrl+C を押すよう Host に依頼します。結果不明の送信済み変更はチャネルを隔離します。変更を再送しないでください。受領記録を保持し、影響する対象を確認し、ユーザーが Host のアイドル状態またはヘルパーの再起動を確認するまで待ってから、明示的な acknowledgeRecovery でバインドします。タイムアウトの詳細にはカウンターだけが含まれ、取得したファイル内容は含まれません。

## 編集と Host 変更

存在しないファイルの読み取りは `not_found` で失敗します。一括読み取りではそのエントリーだけが失敗します。保護付き編集には現在の文書バージョンを使います。dirty バッファーは保護されます。その内容の保持／保存が作業範囲に含まれる場合にだけ対象に含めてください。編集は適用されたが対象の保存に失敗した場合は、テキストを再適用せず、返されたバージョンで保存を再試行します。一括保存はファイル単位で、トランザクションではありません。

Host の書き込みにより、既存の Guest バッファーが古いまま、または dirty のままになることがあります。editor_refresh_pending/external_change_dirty_document はユーザーのエディター全体を revert せずにそれを保持します。影響するバッファーはユーザーと解決するか、安全に開き直してください。明示的な hostStat withTextHash は期待される正規化ダイジェストを更新するもので、エディター自体は更新しません。Guest のテキスト／EOL は Host の生バイトとは別です。Host の Git 設定によってパッチ出力が CRLF に変換されることがあります。

## 検索と言語ツール

Host rg は保存済みファイルを検索します。上限／失敗では complete が false になり、無一致の終了コード 1 は正常です。dirty バッファーは別に一覧され、自動保存されません。スナップショット照会は明示的に不完全なままです。言語操作にはプロバイダーが必要です。プロバイダーがなければエラーになり、診断が空でもビルドやテストの合格を意味しません。

## ファイル操作と制限

バイトの上書きには現在の Host 生 SHA-256 が必要です。ディレクトリコピーは新規宛先が必要で、途中で失敗することがあります。再帰削除と複数ファイルの原子的保存は実装されていません。response_limit の場合は、必要な範囲／少ない結果を要求してください。プロバイダーの部分テキスト応答は、ストリーミング読み取りを意味しません。

大容量ダウンロード（`transferOpenRead`/`transferRead`）は `feature_unavailable` を返します。アクセス可能なコピーとローカルパスをユーザーに依頼し、小分けのバイト読み取りの反復や raw コマンドで制限を迂回しません。小容量のバイト読み取りと大容量アップロードは利用できます。
